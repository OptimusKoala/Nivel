# Nivel 1.14 — Lot D : Frigo et suggestions — Plan d'implémentation

> **Pour les agents :** SOUS-COMPÉTENCE REQUISE — utiliser `superpowers:subagent-driven-development` (recommandé) ou `superpowers:executing-plans` pour exécuter ce plan tâche par tâche.

**But :** proposer chaque jour trois repas légers de saison dans l'onglet Repas, classés selon ce qu'on a dans le frigo, et loggeables en un tap.

**Architecture :** **une recette est un aliment.** Elle entre dans `foods.json` comme plat ordinaire avec sa composition dans `compositions.json` ; un nouveau `recipes.json` ne porte que ce que le catalogue ne sait pas dire — les mois de saison et la préparation. Conséquence : les kcal sortent de `MealEstimator`, la logger c'est `catalog.line(for:)`, et le journal l'affiche déjà correctement. Aucun moteur de calcul nouveau. Le frigo est une liste d'ids sur `UserProfile`, et le classement un calcul pur sans aléatoire.

**Pile :** Swift 6, SwiftUI, SwiftData, XCTest.

**Spec :** `docs/superpowers/specs/2026-08-13-nivel-1.14-design.md` §6.

**Dépendance :** le **lot A** (les ingrédients dont les recettes sont faites) et, pour la seule Task 7, le lot C (les deux badges recette). Aucune sur B.

**Le projet Xcode est généré.** Tout fichier créé — et ce plan en crée cinq — exige **`xcodegen generate`** avant le moindre `xcodebuild` : sans lui un test neuf ne s'exécute pas, et « suite introuvable » ressemble au rouge attendu du TDD avant de devenir un faux vert.

**Il n'y a pas de `NavigationStack` dans l'onglet Repas.** `MealsJournalView` est un `ZStack { VStack { … } }` et `MainTabView` n'enveloppe aucun onglet. Le frigo et la fiche recette se présentent donc **en feuilles** (`.sheet`), comme le ⚙️ de l'accueil présente les Réglages — pas en écrans poussés. Ajouter une pile de navigation autour de l'onglet toucherait `themedTabBar()` et le budget de hauteur que la 1.13 a durement gagné.

> **Noms de test en français.** Les extraits de test de ce plan portent des noms anglais (`testDessertCategoryExists`) : c'est une facilité de rédaction, pas une consigne. Les suites du dépôt sont en français (`testPasDeDoublonDId`, `testUniteEtPoidsVontEnsemble`) — **traduire chaque nom de test au moment de l'écrire**. Le corps et les assertions, eux, se reprennent tels quels.

Dans `FoodCatalog.items(category:slot:)`, la première condition :

```swift
public func items(category: FoodItem.Category, slot: MealSlot?) -> [FoodItem] {
    items.filter { item in
        // Les recettes ont leur propre porte d'entrée (la bande d'idées) : les
        // laisser ici noierait la grille de taps.
        guard !item.isRecipe else { return false }
        guard item.category == category else { return false }
        guard let slot, !item.slots.isEmpty else { return true }
        return item.slots.contains(slot)
    }
}
```

Le `Codable` synthétisé exigerait la clé sur les 122 entrées. **Ne pas le faire** : `FoodItem` reçoit un `init(from:)` explicite avec `decodeIfPresent(Bool.self, forKey: .isRecipe) ?? false`, sur le précédent de `Quest` (`requiresPosture` / `requiresMuscu`). Trois raisons, arbitrées à l'exécution :

1. une clé obligatoire manquante ne casse pas une entrée mais le décodage du catalogue **entier** — et elle manquera un jour, au 123ᵉ aliment ajouté à la main ;
2. ce qu'on veut retrouver au grep, c'est la poignée de recettes, pas les 122 non-recettes ;
3. ~~les oublis d'un `init(from:)` sont des erreurs de compilation, pas des défauts à l'exécution.~~ **FAUX**, démontré par expérience à la revue de qualité : la garantie ne vaut que pour un `let` **sans valeur par défaut**. Un `public var seasonal: Bool = false` ajouté à `FoodItem` compile sans une erreur, ignore `"seasonal": true` dans le JSON, et n'est pas ré-encodé — parce que `CodingKeys` étant manuel, c'est la synthèse d'`Encodable` qui devrait le réclamer, or elle ignore silencieusement une propriété sans clé. Les deux premières raisons suffisent à justifier le choix ; celle-ci était de trop.

Prix assumé : déclarer `init(from:)` supprime l'init memberwise synthétisé, il faut donc en réécrire un (12 paramètres, `isRecipe: Bool = false`). Et surtout, **`CodingKeys` devient une liste à maintenir à la main** : mettre un commentaire au-dessus disant qu'un champ ajouté avec un défaut sur sa déclaration n'y sera **pas** réclamé par le compilateur, donc que tout nouveau champ de `FoodItem` s'écrit `let` sans défaut. La forme piégée est exactement celle qu'on écrit spontanément, et celle que §6.3 emploie pour le frigo.

`foods.json` n'est **pas** touché par cette tâche — les recettes y entrent à la Task 2, avec `"isRecipe": true`.

**Deux tests de plus que le plan d'origine ne prévoyait pas**, et sans eux la tâche entière survit à sa propre suppression (mutation vérifiée : retirer le `guard` laisse 230 verts, renommer la clé JSON aussi) :

- `testLeFiltreEcarteUneRecetteDeSaCategorie` — un `FoodCatalog` de laboratoire à deux items, dont une recette. Le vrai catalogue ne peut rien affirmer tant qu'il n'a aucune recette.
- `testLaCleIsRecipeSeDecodeDepuisLeJSON` — décodage direct d'un `[FoodItem]` littéral portant `"isRecipe": true`. Épingle le nom de la clé et le défaut.

```swift
// Recette de saison (spec v1.14 §6.2). Ne porte QUE ce que le catalogue
// d'aliments ne sait pas dire : les mois où la recette a du sens, et sa
// préparation. Le nom, l'emoji, les créneaux, les ingrédients et les kcal vivent
// sur le FoodItem correspondant — une seule vérité par donnée.

import Foundation

public struct Recipe: Codable, Identifiable, Hashable, Sendable {
    /// Id du `FoodItem` marqué `isRecipe` qui porte le reste.
    public let itemID: String
    /// Mois (1-12) où la recette est de saison.
    public let months: [Int]
    /// Trois à quatre lignes de préparation, au ton de Nivelito : on encourage,
    /// on ne donne pas d'ordre.
    public let steps: [String]

    public var id: String { itemID }

    public func isInSeason(month: Int) -> Bool { months.contains(month) }
}

/// Catalogue chargé une fois. Repli vide si le JSON est corrompu : la bande
/// d'idées disparaît, l'app continue — même règle que les six autres catalogues.
public struct RecipeCatalog: Sendable {
    public let recipes: [Recipe]
    public let byItemID: [String: Recipe]

    public init(recipes: [Recipe]) {
        self.recipes = recipes
        self.byItemID = Dictionary(recipes.map { ($0.itemID, $0) }, uniquingKeysWith: { a, _ in a })
    }

    public static let empty = RecipeCatalog(recipes: [])

    public static func load() throws -> RecipeCatalog {
        RecipeCatalog(recipes: try Catalogs.recipes())
    }
}
```

> **Pourquoi les trois tests ci-dessous font `guard let … else { continue }` et non `byID[...]!`.** XCTest exécute les tests d'une classe par ordre alphabétique, et les trois nouveaux (`testChaque…`, `testLeRepli…`) passent **avant** `testLesRecettesSeChargentEtPointentVersDeVraisAliments`, le seul qui sache nommer une recette sans aliment. Un déballage forcé tuerait le processus sur un `signal 5` muet avant que le diagnostic n'ait la parole. C'est exactement le piège trouvé à la Task 2, sous une autre forme — et la règle est déjà écrite dans le dépôt, à `BadgeEngineTests.swift:104-105`.
>
> Les deux `byID[...]!` de la Task 5 sont, eux, acceptables : `RecipeCatalogTests` passe avant `RecipeSuggesterTests` (C < S), donc la faute y est nommée avant d'être rencontrée.

> **Deux données de la Task 2 à reprendre ici**, héritées de l'exemple du plan et laissées en place pour ne pas dévier de la Task 2 : la composition de `cod_papillote` porte `lettuce` 20 g, et ses étapes parlent de courgettes et de citron.
```swift
func testCatalogueSize() throws {
    XCTAssertEqual(try Catalogs.recipes().count, 35)

/// Aucun mois sans idée, ni pour le midi ni pour le soir. Le seuil est QUATRE et
/// non trois : la bande en montre trois, et il faut au moins une candidate de
/// rab pour que la rotation du jour ait de quoi tourner (spec §6.4 règle 7).
func testEveryMonthHasFourIdeasPerSlot() throws {
    let recipes = try Catalogs.recipes()
    let catalog = try FoodCatalog.load()
    for month in 1...12 {
        for slot in [MealSlot.lunch, .dinner] {
            let count = recipes.filter { recipe in
                recipe.months.contains(month)
                    && (catalog.byID[recipe.itemID]?.slots.contains(slot) ?? false)
            }.count
            XCTAssertGreaterThanOrEqual(count, 4, "mois \(month), créneau \(slot)")
        }
    }
}

/// Chaque ingrédient d'une recette doit être un `.side` : `PantryView` ne liste
/// que ceux-là, donc une recette citant un plat ou un encas ne pourrait JAMAIS
/// atteindre la couverture complète dans l'app réelle — la carte afficherait
/// « il manque 1 » à vie, sans que rien ne l'explique.
func testRecipeComponentsAreAllIngredients() throws {
    let catalog = try FoodCatalog.load()
    for recipe in try Catalogs.recipes() {
        guard let item = catalog.byID[recipe.itemID] else { continue }
        for component in catalog.line(for: item).components {
            XCTAssertEqual(catalog.byID[component.itemID]?.category, .side,
                           "\(recipe.itemID) → \(component.itemID) n'est pas un ingrédient")
        }
    }
}

/// Le repli du plat composé (spec §3.1) : `kcalPer100g × defaultGrams` doit rester
/// à ~10 % du total de la composition. Rien ne le vérifiait pour des entrées
/// écrites à la main, et un repli faux ne se voit que le jour où il sert.
func testRecipeFallbackMatchesItsComposition() throws {
    let catalog = try FoodCatalog.load()
    for recipe in try Catalogs.recipes() {
        guard let item = catalog.byID[recipe.itemID] else { continue }
        let composed = MealEstimator.kcal(lines: [catalog.line(for: item)],
                                          kcalPer100g: catalog.kcalPer100g)
        let fallback = item.kcalPer100g * Double(item.defaultGrams) / 100
        XCTAssertEqual(fallback, Double(composed), accuracy: Double(composed) * 0.1,
                       "\(recipe.itemID) : repli \(Int(fallback)) vs composition \(composed)")
    }
}

/// Une suggestion « légère » qui dépasse 500 kcal n'est pas une suggestion légère.
func testEveryRecipeStaysUnderFiveHundred() throws {
    let catalog = try FoodCatalog.load()
    for recipe in try Catalogs.recipes() {
        guard let item = catalog.byID[recipe.itemID] else { continue }
        let kcal = MealEstimator.kcal(lines: [catalog.line(for: item)],
                                      kcalPer100g: catalog.kcalPer100g)
        XCTAssertLessThanOrEqual(kcal, 520, "\(recipe.itemID) : \(kcal) kcal")
    }
}
```

C'est la tâche la plus subtile du lot, et elle porte **deux pièges dont chacun rendrait la fonctionnalité silencieusement inutile** :

**Piège 1 — la rotation ne doit pas être écrasée par le tri.** Décaler la liste des candidates puis les trier avec le décalage comme dernière clé de comparaison ne change *rien* : dès que deux recettes diffèrent en kcal (c'est-à-dire presque toujours, les kcal étant des entiers), le tri les ordonne indépendamment du décalage. **Piège 2 — classer sur le NOMBRE d'ingrédients manquants est faux.** Frigo vide, `missingCount` vaut le nombre d'ingrédients, qui varie d'une recette à l'autre : une recette de 3 ingrédients à 500 kcal passerait devant une de 4 ingrédients à 300 kcal. Le classement se fait sur le **taux** de couverture (présents / total), qui vaut 0 partout quand le frigo est vide — et le tri retombe alors sur les kcal, comme la spec l'exige.

```swift
// NivelCore/Sources/NivelCore/RecipeSuggester.swift
// Classement des suggestions de repas (spec v1.14 §6.4). Pur et SANS aléatoire :
// la bande doit être identique à chaque ouverture d'un même jour, et testable.

import Foundation

/// Une suggestion prête à afficher : la recette, ses kcal calculées et l'état du
/// frigo la concernant.
public struct RecipeSuggestion: Sendable, Equatable {
    public let recipe: Recipe
    public let kcal: Int
    public let ingredientCount: Int
    public let missingCount: Int

    public var hasEverything: Bool { missingCount == 0 }

    /// TAUX de couverture (0…1), et c'est lui qui classe — jamais `missingCount`.
    /// Frigo vide, le nombre d'ingrédients manquants vaut le nombre d'ingrédients,
    /// qui varie d'une recette à l'autre : classer là-dessus ferait passer une
    /// recette de 3 ingrédients à 500 kcal devant une de 4 à 300 kcal. Le taux,
    /// lui, vaut 0 partout, et le tri retombe proprement sur les kcal.
    public var coverage: Double {
        guard ingredientCount > 0 else { return 0 }
        return Double(ingredientCount - missingCount) / Double(ingredientCount)
    }
}

public enum RecipeSuggester {
    public static func suggestions(
        date: Date,
        slot: MealSlot,
        pantry: Set<String>,
        recipes: RecipeCatalog,
        catalog: FoodCatalog,
        calendar: Calendar,
        limit: Int = 3
    ) -> [RecipeSuggestion] {
        guard limit > 0 else { return [] }
        let month = calendar.component(.month, from: date)

        // Le créneau ne se relâche JAMAIS : proposer un déjeuner le soir n'aide
        // personne. Le mois, si — mieux vaut une idée hors saison qu'une bande
        // vide au 1ᵉʳ février.
        let inSlot = recipes.recipes.filter {
            catalog.byID[$0.itemID]?.slots.contains(slot) ?? false
        }
        let inSeason = inSlot.filter { $0.isInSeason(month: month) }
        let candidates = inSeason.isEmpty ? inSlot : inSeason
        guard !candidates.isEmpty else { return [] }

        let scored = candidates.map { score($0, pantry: pantry, catalog: catalog) }

        // 1. Ce dont on a TOUT passe devant, trié aux kcal, et n'est jamais soumis
        //    à la rotation : ce qu'on peut cuisiner sans ressortir doit rester
        //    proposé tous les jours.
        let complete = scored.filter(\.hasEverything).sorted(by: byCoverageThenKcal)
        var chosen = Array(complete.prefix(limit))

        // 2. Le reste passe par une liste COURTE que le jour fait tourner. C'est
        //    la seule façon que la rotation change quelque chose : appliquée à
        //    l'ordre final, elle serait écrasée par le tri sur les kcal, et la
        //    bande afficherait les mêmes plats tout le mois.
        let remaining = limit - chosen.count
        if remaining > 0 {
            let rest = scored.filter { !$0.hasEverything }.sorted(by: byCoverageThenKcal)
            let shortlist = Array(rest.prefix(limit * 3))
            if !shortlist.isEmpty {
                let dayOfYear = calendar.ordinality(of: .day, in: .year, for: date) ?? 0
                let offset = dayOfYear % shortlist.count
                let rotated = Array(shortlist[offset...] + shortlist[..<offset])
                chosen += rotated.prefix(remaining)
            }
        }

        // 3. L'affichage, lui, est toujours ordonné : couverture puis kcal.
        return chosen.sorted(by: byCoverageThenKcal)
    }

    private static func score(_ recipe: Recipe, pantry: Set<String>,
                              catalog: FoodCatalog) -> RecipeSuggestion {
        let line = catalog.byID[recipe.itemID].map { catalog.line(for: $0) }
        let ids = line?.components.map(\.itemID) ?? []
        return RecipeSuggestion(
            recipe: recipe,
            kcal: MealEstimator.kcal(lines: line.map { [$0] } ?? [],
                                     kcalPer100g: catalog.kcalPer100g),
            ingredientCount: ids.count,
            missingCount: ids.filter { !pantry.contains($0) }.count
        )
    }

    /// Tri total et déterministe : couverture décroissante, kcal croissantes, puis
    /// l'id en dernier recours — sans cette dernière clé, deux recettes également
    /// couvertes et de mêmes kcal s'ordonneraient au gré du fichier.
    private static func byCoverageThenKcal(_ left: RecipeSuggestion,
                                          _ right: RecipeSuggestion) -> Bool {
        if left.coverage != right.coverage { return left.coverage > right.coverage }
        if left.kcal != right.kcal { return left.kcal < right.kcal }
        return left.recipe.itemID < right.recipe.itemID
    }
}
```
