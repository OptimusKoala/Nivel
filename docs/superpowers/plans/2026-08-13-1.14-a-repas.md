# Nivel 1.14 — Lot A : Repas — Plan d'implémentation

> **Pour les agents :** SOUS-COMPÉTENCE REQUISE — utiliser `superpowers:subagent-driven-development` (recommandé) ou `superpowers:executing-plans` pour exécuter ce plan tâche par tâche. Les étapes sont des cases à cocher (`- [ ]`).

**But :** porter le catalogue d'aliments de 85 à 122 entrées, ajouter une cinquième catégorie « Desserts », et rendre impossible la perte d'un panier de repas par fermeture accidentelle.

**Architecture :** presque tout est de la donnée. La 1.10 a posé qu'un plat est une ligne composée (`MealLine.composed`) dont `MealEstimator` somme les composants ; le `kcalPer100g` du plat parent n'est jamais lu pour une ligne composée. Ajouter un plat = une entrée dans `foods.json` + sa composition dans `compositions.json`. Seuls le sélecteur de catégories (cinq segments ne tiennent plus) et le garde de fermeture touchent du Swift.

**Pile :** Swift 6, SwiftUI, SwiftData, XCTest. Logique pure dans le paquet `NivelCore`, interface dans `App/`.

**Spec :** `docs/superpowers/specs/2026-08-13-nivel-1.14-design.md` §3. Les tableaux de valeurs (ids, kcal, compositions) y sont : **ne pas les recopier ici, les lire là-bas**.

**Le projet Xcode est généré.** `Nivel.xcodeproj` n'a aucun groupe synchronisé : chaque fichier y est référencé explicitement. La Task 6 crée un fichier de test, qui exige donc **`xcodegen generate`** avant le moindre `xcodebuild` — sans lui la suite n'est pas compilée, et le « suite introuvable » qui en résulte ressemble au rouge attendu du TDD avant de devenir un faux vert.

> **Noms de test en français.** Les extraits de test de ce plan portent des noms anglais (`testDessertCategoryExists`) : c'est une facilité de rédaction, pas une consigne. Les suites du dépôt sont en français (`testPasDeDoublonDId`, `testUniteEtPoidsVontEnsemble`) — **traduire chaque nom de test au moment de l'écrire**. Le corps et les assertions, eux, se reprennent tels quels.

**Commandes de test :**
```bash

cd NivelCore && swift test --filter FoodCatalogTests
```

```swift
func testNewDishesHaveResolvableCompositions() throws {
    let catalog = try FoodCatalog.load()
    let newDishes = ["tacos", "kebab", "burrata_tomato", "apero_platter",
                     "fried_chicken_salad", "nuggets_meal", "omelette",
                     "omelette_garnie", "gratin_dauphinois", "gratin_veg",
                     "gratin_pasta", "asian_noodles", "oatmeal_fruit", "breakfast_eggs"]
    for id in newDishes {
        guard let item = catalog.byID[id] else { return XCTFail("plat manquant : \(id)") }
        XCTAssertEqual(item.category, .dish, "\(id)")
        let line = catalog.line(for: item)
        XCTAssertTrue(line.isComposed, "\(id) doit avoir une composition")
        for component in line.components {
            XCTAssertNotNil(catalog.byID[component.itemID],
                            "\(id) référence un ingrédient inconnu : \(component.itemID)")
            XCTAssertGreaterThan(component.grams, 0, "\(id)/\(component.itemID)")
        }
    }
}

/// Deux valeurs témoins : si un barème d'ingrédient bouge, ces deux-là le disent.
func testSpotCheckedEstimates() throws {
```

Composition et créneaux exacts : **spec §3.3**. Dans `foods.json`, chaque plat suit ce modèle (le `kcalPer100g` d'un plat composé n'est jamais lu par l'estimation — il vaut le total de la composition ramené à 100 g, comme les quinze plats composés existants ; `other` est le seizième plat, délibérément sans composition, cf. `testAutreNAPasDeComposition`) :

```json
"tacos": [
```

```swift
/// Deux entrées homonymes DANS LE MÊME ONGLET sont un piège : on tape l'une en
/// croyant taper l'autre. D'un onglet à l'autre, en revanche, l'homonymie est
/// légitime et voulue — « Fromage » existe en ingrédient (350 kcal/100 g, pour
/// une composition) ET en encas, « Céréales » en plat ET en ingrédient. C'est
/// donc l'unicité PAR CATÉGORIE qu'il faut exiger, pas l'unicité globale.
func testNamesAreUniqueWithinACategory() throws {
    let items = try FoodCatalog.load().items
    for category in FoodItem.Category.allCases {
        let names = items.filter { $0.category == category }.map(\.name)
        XCTAssertEqual(Set(names).count, names.count,
                       "\(category) : \(Dictionary(grouping: names, by: { $0 }).filter { $0.value.count > 1 }.keys)")
    }
}

/// Le tag que lit la quête « jours en dessert léger » (GameService). Les nouveaux
/// desserts gourmands DOIVENT le porter : sans lui, la quête serait satisfaite en
/// mangeant une pâtisserie à 380 kcal/100 g — exactement le bug que

        XCTAssertFalse(catalog.hasTag("richDessert", itemID: id), "\(id) n'est pas gourmand")
```

- [ ] **Étape 1 : remplacer le `Picker` segmenté**

Cinq segments ne tiennent pas dans la largeur d'un iPhone, et le Dynamic Type les achève. Le contrôle devient une rangée de pastilles défilantes, **calquée sur les pastilles de créneau de `MealLogSheet.slotPicker`** — un seul motif de sélection dans la feuille plutôt que deux — **avec trois ajouts que `slotPicker` n'a pas encore** : la cible tactile de 44 pt, le libellé d'accessibilité et le trait de sélection. Ces trois-là ne sont pas des divergences accidentelles à harmoniser plus tard : le `Picker` segmenté remplacé portait la sémantique de sélection nativement pour VoiceOver, un `Button` nu ne l'a pas. C'est `slotPicker` qui devra rattraper (Task 6), pas l'inverse.

```swift
private var categoryPicker: some View {
    ScrollView(.horizontal, showsIndicators: false) {
        HStack(spacing: 8) {
            ForEach(FoodItem.Category.tabOrder, id: \.self) { candidate in
                Button {
                    category = candidate
                } label: {
                    Text(candidate.frLabel)
                        .font(.footnote.weight(.semibold))
                        .padding(.horizontal, 13)
                        .padding(.vertical, 9)
                        .background(category == candidate ? Theme.orange : Theme.card,
                                    in: Capsule())
                        .foregroundStyle(category == candidate ? .white : Theme.text)
                        // 44 pt de cible tactile (règle Apple), la pastille seule
                        // n'atteignant que 36 pt de haut.
                        .frame(minHeight: 44)
                        .contentShape(Rectangle())
                        .animation(.snappy, value: category)
                }
                .buttonStyle(.plain)
                .accessibilityLabel("Catégorie \(candidate.frLabel)")
                .accessibilityAddTraits(category == candidate ? [.isSelected] : [])
            }
        }
    }
}
```

L'affectation reste nue et l'animation se porte sur le label, pas sur la mutation : `category`
conditionne aussi le contenu de la grille juste en dessous (`items`), et une `withAnimation`
englobante lui ferait jouer une animation d'insertion/suppression sur chaque carte à chaque
changement d'onglet — jusqu'à 58 d'un coup pour l'onglet Ingrédients. Le clip par défaut de la
`ScrollView` suffit : pas besoin de `.scrollClipDisabled()` ni de marge de compensation, le fond
des pastilles est une capsule nue sans halo à protéger.

Et dans `body`, `Picker` devient `categoryPicker`. `lockedCategory` continue de masquer entièrement le sélecteur : rien à changer de ce côté.

```swift
// NivelTests/MealLogSheetDismissTests.swift
// Garde de fermeture de la feuille de repas (spec v1.14 §3.6) : un panier garni
// ne se jette pas d'un glissement. La décision est pure, la vue ne fait que
// l'appliquer.
import XCTest
import NivelCore
@testable import Nivel

final class MealLogSheetDismissTests: XCTestCase {
    func testEmptyBasketClosesWithoutAsking() {
        XCTAssertFalse(MealLogSheet.guardsDismissal(lines: []))
    }

    func testFilledBasketAsksBeforeClosing() {
        let line = MealLine.simple(MealComponent(itemID: "beer_half", grams: 500))
        XCTAssertTrue(MealLogSheet.guardsDismissal(lines: [line]))
    }

    /// Un panier composé garde le garde : la règle porte sur « il y a du contenu »,
    /// pas sur la forme des lignes.
    func testComposedBasketAlsoGuards() {
        let catalog = try! FoodCatalog.load()
        let line = catalog.line(for: catalog.byID["tacos"]!)
        XCTAssertTrue(line.isComposed)
        XCTAssertTrue(MealLogSheet.guardsDismissal(lines: [line]))
    }
}
```

- [ ] **Étape 3 : implémenter**

Dans `MealLogSheet` :

```swift
/// Vrai quand fermer la feuille détruirait du travail. Pure et testée
/// (MealLogSheetDismissTests) : la vue ne fait que l'appliquer. Le garde s'arme
/// exactement quand la feuille est enregistrable — même prédicat que le `.disabled`
/// du CTA, et ce n'est pas une coïncidence.
static func guardsDismissal(lines: [MealLine]) -> Bool { !lines.isEmpty }

/// La même décision appliquée au panier courant. La statique existe pour le test,
/// celle-ci pour la vue, qui l'interroge à trois endroits.
private var guardsDismissal: Bool { Self.guardsDismissal(lines: lines) }

@State private var showAbandonDialog = false
```

Dans `body`, après `.presentationDragIndicator(…)` :

```swift
.interactiveDismissDisabled(guardsDismissal)
```

> Depuis, cet indicateur n'est plus inconditionnel : il se masque quand le garde est armé (spec §3.6, commit séparé). Ne pas recopier `.visible` tel quel.

Dans la `NavigationStack`, une barre d'outils :

```swift
.toolbar {
    // Sortie VISIBLE : dès qu'on empêche le glissement, il faut en offrir une.
    ToolbarItem(placement: .topBarLeading) {
        Button {
            if guardsDismissal {
                showAbandonDialog = true
            } else {
                dismiss()
            }
        } label: {
            // Pas de `.font` réduite, et pas de `.frame(minWidth:minHeight:)` de 44 pt :
            // le chrome de barre d'outils dessine déjà 61 × 60 pt (mesuré), et l'imposer
            // transformerait le cercle en capsule. Voir le commentaire du fichier.
            Image(systemName: "xmark")
        }
        .tint(Theme.subtext)
        .accessibilityLabel("Fermer")
        // La croix est la seule sortie une fois le garde armé, et `validate()` lance
        // un Task non structuré : sans ça, « Abandonner » pourrait ne rien abandonner.
        .disabled(isSaving)
    }
}
.confirmationDialog(isEditing ? "Abandonner les modifications ?" : "Abandonner ce repas ?",
                    isPresented: $showAbandonDialog,
                    titleVisibility: .visible) {
    // PAS de `role: .destructive` : un bouton destructif de confirmationDialog est
    // peint en rouge par le système et refuse d'être teinté (contrairement à une
    // action de glissement, cf. SportView). Un bouton ordinaire est la seule façon
    // de respecter « jamais de rouge » (règle v1 §7.4) dans un dialogue.
    Button("Abandonner") { dismiss() }
    Button("Reprendre", role: .cancel) {}
} message: {
    // Textes conditionnés au mode : en édition, le repas EST enregistré, et « ton panier
    // n'est pas encore enregistré » mentirait sur l'état des données. Le message dit ce
    // qui reste, pas ce qui se perd.
    Text(isEditing ? "Ce repas restera tel qu'il était."
                   : "Ton panier n'est pas encore enregistré.")
}
```

Le titre de l'écran (`Text(isEditing ? "Modifier le repas" : "Nouveau repas")`) reste dans le contenu défilant : le mettre en `navigationTitle` mangerait de la hauteur, ce que la 1.13 a passé son temps à récupérer.
