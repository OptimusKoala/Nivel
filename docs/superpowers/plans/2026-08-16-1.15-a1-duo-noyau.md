# Nivel 1.15 — Lot A1 : le duo, noyau et publication — Plan d'implémentation

> **Pour les agents :** SOUS-COMPÉTENCE REQUISE — utiliser `superpowers:subagent-driven-development` (recommandé) ou `superpowers:executing-plans` pour exécuter ce plan tâche par tâche.

**But :** tout ce qui se teste sans nuage et sans écran — les formes publiées, la construction du fil, l'identité d'un événement, les textes de Nivelito, les capacités du projet, et la publication d'un instantané dans une zone iCloud.

**Architecture :** on ne miroite rien. Le magasin SwiftData reste la seule source de vérité, et un `DuoPublisher` écrit à côté un petit instantané dans une zone iCloud partagée — exactement comme `syncWidget()` écrit le sien dans l'App Group depuis la v1.6. Tout ce qui se décide sans réseau vit dans NivelCore et est testé ; ce qui parle à CloudKit est mince et concentré dans deux fichiers.

**Pile :** Swift 6, SwiftData, CloudKit, XCTest.

**Spec :** `docs/superpowers/specs/2026-08-16-nivel-1.15-design.md` §3.1 à §3.5.

**Dépendances :** aucune sur les lots B, C, D. **Le lot A2 dépend entièrement de celui-ci.**

> Les divergences connues, par gravité :
>
> 1. **Task 1 — `Kind` sans cas `unknown`.** Le plan donne un enum à deux cas. Un seul genre inconnu fait alors échouer le décodage du **fil entier**, et un partenaire resté en 1.15 ne verrait plus aucun événement. Voir spec §3.4.
> 2. **Task 4 — rien sur les cœurs orphelins.** Ni `orphanEventIDs`, ni la règle « un orphelin se juge sur le magasin, jamais sur le fil du jour ». La première rédaction de cette règle **effaçait chaque nuit tous les cœurs de la veille**. Voir spec §3.4.

> 5. **Task 6 — `cloudKitDatabase: .none` totalement absent**, alors que c'est précisément cette tâche qui, en ajoutant l'entitlement iCloud, fait **planter l'app au lancement** sans ce paramètre. Voir spec §3.2.
> 6. **Task 6 — `aps-environment: development` en dur.** Livré par variable de configuration, avec trois vérifications à l'export dans `release.sh`.
>
> Deux erreurs de détail du plan, sans gravité mais qui feraient perdre du temps : le test de la Task 3 attend `« déjeuner, ~420 kcal »` alors que `MealFormatting.frKcal`, que la même page ordonne de réutiliser, produit `« ~ 420 kcal »` avec une espace ; et le tableau des fichiers est faux sur quatre lignes (`DuoBadge` a son propre fichier, les tests sont répartis autrement, et `GameService+DuoSnapshot.swift` n'y figure pas).

## ⚠️ Cinq règles de ce dépôt, à ne pas redécouvrir en cours de route

**1. Le projet Xcode est généré.** Aucun groupe synchronisé : chaque fichier est référencé explicitement. **Tout fichier créé exige `xcodegen generate`** avant le moindre `xcodebuild`, sinon l'erreur observée est « classe de test introuvable » et non celle qu'on attend. Ce plan crée huit fichiers ; la commande apparaît à chaque fois.

**2. Un défaut de déclaration SwiftData n'est pas une valeur par ligne.** Le projet ajoute des champs avec un défaut sur la déclaration depuis la v1 pour rester en migration légère. Mais un défaut n'est **pas** une garantie d'unicité : `var publicID: String = UUID().uuidString` risquerait de donner **le même identifiant** à toutes les entrées existantes. La Task 2 utilise donc la chaîne vide comme sentinelle et remplit à la volée. Ne pas « simplifier » ce choix.

**3. Un contexte de message exige douze textes.** `MessageContext` est un enum fermé, `MessageBank.load` déclenche `assertionFailure` sur une clé absente, et `MessageBankTests.testBankHasAllContextsWithEnoughVariety` exige **≥ 12 messages par contexte**. Un contexte ajouté sans ses textes rend `messages(for:)` vide et fait retomber la bulle sur « Salut {name} ! », **silencieusement en release**. Les deux s'ajoutent dans la même tâche.

**4. `pick(name:)` reçoit ici le prénom du PARTENAIRE.** Dans tous les autres contextes, `{name}` est le prénom de l'utilisateur. Pour `duoLikeReceived`, c'est celui de l'autre : « {name} a aimé ce que tu as noté ». C'est le seul endroit du dépôt où ce paramètre change de sens, et c'est écrit dans le commentaire de l'enum pour que ça ne surprenne personne.

**5. Aucun tiret cadratin dans les ressources.** `testNoBundleResourceContainsEmDash` balaie toutes les ressources du bundle, `messages.json` compris.

// NivelCore/Tests/NivelCoreTests/DuoSnapshotTests.swift
import XCTest
@testable import NivelCore

final class DuoSnapshotTests: XCTestCase {

    private func instantane(generatedAt: Date = Date(timeIntervalSince1970: 1_000)) -> DuoSnapshot {
        DuoSnapshot(
            memberID: "M1", name: "Marion", sexRaw: "female",
            level: 11, totalXP: 2_340, xpIntoLevel: 140, xpForNextLevel: 220,
            dayKey: "2026-08-16",
            kcalEaten: 1_180, kcalTarget: 1_550, burned: 310, burnTarget: 400, steps: 7_240,
            quest: DuoQuestLine(title: "Bouger 4 fois", done: 3, total: 4),
            events: [], generatedAt: generatedAt
        )
    }

    /// LE test qui évite les écritures inutiles (spec §3.5) : deux instantanés qui ne
    /// diffèrent QUE par leur horodatage sont le même instantané. Sans cette règle,
    /// chaque appel de la publication écrirait dans iCloud alors que rien n'a bougé.
    func testLEgaliteIgnoreLHorodatage() {
        XCTAssertEqual(instantane(), instantane(generatedAt: Date(timeIntervalSince1970: 9_999)))
    }

    /// La contrepartie : tout le reste compte.
    func testUnChiffreQuiChangeRendLesInstantanesDifferents() {
        var autre = instantane()
        autre.kcalEaten += 1
        XCTAssertNotEqual(instantane(), autre)
    }

    /// Les pas sont absents tant que HealthKit n'a pas répondu, et absents pour
    /// toujours s'il est refusé. `-1` porte les deux cas, comme `DailySteps.unavailable`
    /// côté app : un `0` ferait afficher « 0 pas » à quelqu'un qui a marché.
    func testLesPasIndisponiblesSeCodentEnMoinsUn() throws {
        let json = try JSONEncoder().encode(instantane())
        let relu = try JSONDecoder().decode(DuoSnapshot.self, from: json)
        XCTAssertEqual(relu.steps, 7_240)
        XCTAssertEqual(DuoSnapshot.stepsUnavailable, -1)
    }

    /// Compatibilité ascendante (spec §3.4) : un instantané venu d'une version plus
    /// récente, avec une clé de plus, doit se décoder sans erreur chez qui ne la
    /// connaît pas. `JSONDecoder` ignore les clés inconnues, ce test le pinne.
    func testUneCleInconnueNeCassePasLeDecodage() throws {
        var objet = try XCTUnwrap(
            try JSONSerialization.jsonObject(with: JSONEncoder().encode(instantane()))
                as? [String: Any])
        objet["champDUneVersionFuture"] = "peu importe"
        let donnees = try JSONSerialization.data(withJSONObject: objet)
        XCTAssertNoThrow(try JSONDecoder().decode(DuoSnapshot.self, from: donnees))
    }

    /// Un événement se code et se relit à l'identique.
    func testUnEvenementFaitLAllerRetour() throws {
        let evenement = DuoEvent(id: "E1", kind: .meal, at: Date(timeIntervalSince1970: 5_000),
                                 title: "Salade de lentilles", subtitle: "déjeuner, ~420 kcal")
        let relu = try JSONDecoder().decode(
            DuoEvent.self, from: try JSONEncoder().encode(evenement))
        XCTAssertEqual(relu, evenement)
    }
}
```

// NivelCore/Sources/NivelCore/DuoSnapshot.swift
// Ce qu'un membre du duo publie (spec 1.15 §3.3). Types PURS : aucun import de
// CloudKit ici, c'est ce qui rend le contrat testable sans réseau.

import Foundation

public struct DuoQuestLine: Codable, Equatable, Sendable {
    public let title: String
    public let done: Int
    public let total: Int

    public init(title: String, done: Int, total: Int) {
        self.title = title
        self.done = done
        self.total = total
    }
}

public struct DuoEvent: Codable, Equatable, Identifiable, Sendable {
    public enum Kind: String, Codable, Sendable { case meal, activity }

    /// `publicID` de l'entrée locale (spec §3.4). C'est la cible d'un cœur.
    public let id: String
    public let kind: Kind
    public let at: Date
    /// Calculés à la PUBLICATION, jamais à l'affichage : le partenaire n'a pas à
    /// posséder les mêmes catalogues, et une entrée de catalogue que sa version ne
    /// connaît pas s'affiche quand même correctement.
    public let title: String
    public let subtitle: String

    public init(id: String, kind: Kind, at: Date, title: String, subtitle: String) {
        self.id = id
        self.kind = kind
        self.at = at
        self.title = title
        self.subtitle = subtitle
    }
}

public struct DuoSnapshot: Codable, Sendable {
    /// Sentinelle des pas indisponibles. Le miroir de `DailySteps.unavailable` côté
    /// app : HealthKit refusé et lecture pas encore revenue donnent le même `-1`,
    /// et l'affichage masque la ligne au lieu d'écrire « 0 pas ».
    public static let stepsUnavailable = -1

    public let memberID: String
    public var name: String
    public var sexRaw: String
    public var level: Int
    public var totalXP: Int
    /// Publiés DÉJÀ CALCULÉS, jamais le seul `totalXP` à interpréter (spec §3.4) :
    /// les deux téléphones peuvent tourner sur deux courbes de niveaux différentes,
    /// et `levelCurveVersion` ne doit jamais être remise en cause.
    public var xpIntoLevel: Int
    public var xpForNextLevel: Int
    public var dayKey: String
    public var kcalEaten: Int
    public var kcalTarget: Int
    public var burned: Int
    public var burnTarget: Int
    public var steps: Int
    public var quest: DuoQuestLine?
    public var events: [DuoEvent]
    /// EXCLU de l'égalité — voir `==` plus bas.
    public var generatedAt: Date

    public init(memberID: String, name: String, sexRaw: String,
                level: Int, totalXP: Int, xpIntoLevel: Int, xpForNextLevel: Int,
                dayKey: String, kcalEaten: Int, kcalTarget: Int,
                burned: Int, burnTarget: Int, steps: Int,
                quest: DuoQuestLine?, events: [DuoEvent], generatedAt: Date) {
        self.memberID = memberID; self.name = name; self.sexRaw = sexRaw
        self.level = level; self.totalXP = totalXP
        self.xpIntoLevel = xpIntoLevel; self.xpForNextLevel = xpForNextLevel
        self.dayKey = dayKey
        self.kcalEaten = kcalEaten; self.kcalTarget = kcalTarget
        self.burned = burned; self.burnTarget = burnTarget; self.steps = steps
        self.quest = quest; self.events = events; self.generatedAt = generatedAt
    }
}

extension DuoSnapshot: Equatable {
    /// `generatedAt` est DÉLIBÉRÉMENT absent (spec §3.5). C'est cette égalité que la
    /// publication interroge pour décider d'écrire : la comparer horodatage compris
    /// rendrait chaque instantané différent du précédent, et l'app écrirait dans
    /// iCloud à chaque passage au premier plan sans qu'aucun chiffre ait bougé.
    public static func == (a: DuoSnapshot, b: DuoSnapshot) -> Bool {
        a.memberID == b.memberID && a.name == b.name && a.sexRaw == b.sexRaw
            && a.level == b.level && a.totalXP == b.totalXP
            && a.xpIntoLevel == b.xpIntoLevel && a.xpForNextLevel == b.xpForNextLevel
            && a.dayKey == b.dayKey
            && a.kcalEaten == b.kcalEaten && a.kcalTarget == b.kcalTarget
            && a.burned == b.burned && a.burnTarget == b.burnTarget
            && a.steps == b.steps && a.quest == b.quest && a.events == b.events
    }
}
```

// NivelCore/Tests/NivelCoreTests/DuoFeedBuilderTests.swift
import XCTest
@testable import NivelCore

final class DuoFeedBuilderTests: XCTestCase {

    private let midi = Date(timeIntervalSince1970: 1_786_960_800)   // 12:40
    private var apresMidi: Date { midi.addingTimeInterval(5_700) }  // 14:15

    /// Le fil est trié du plus ancien au plus récent : c'est l'ordre d'une journée
    /// qu'on relit, pas d'un fil d'actualité.
    func testLeFilEstTrieParHeureCroissante() {
        let fil = DuoFeedBuilder.build(
            meals: [.init(publicID: "M1", date: apresMidi, slot: .snack,
                          title: "Fruits coupés", kcal: 90, isManual: false)],
            activities: [.init(publicID: "A1", date: midi, title: "Vélo tranquille",
                               durationMinutes: 20, xp: 30)])
        XCTAssertEqual(fil.map(\.id), ["A1", "M1"])
    }

    /// Les sous-titres, mot pour mot. Ils sont calculés ici et JAMAIS à l'affichage.
    func testLesSousTitresSontCalculesALaPublication() {
        let fil = DuoFeedBuilder.build(
            meals: [.init(publicID: "M1", date: midi, slot: .lunch,
                          title: "Salade de lentilles", kcal: 420, isManual: false)],
            activities: [.init(publicID: "A1", date: apresMidi, title: "Vélo tranquille",
                               durationMinutes: 20, xp: 30)])
        XCTAssertEqual(fil[0].subtitle, "déjeuner, ~420 kcal")
        XCTAssertEqual(fil[0].kind, .meal)
        XCTAssertEqual(fil[1].subtitle, "20 min, +30 XP")
        XCTAssertEqual(fil[1].kind, .activity)
    }

    /// Des kcal SAISIES À LA MAIN ne portent pas le « ~ » : la même règle que le
    /// journal Repas depuis la 1.10 (`MealFormatting.frKcal`). Le duo ne doit pas
    /// être le seul endroit de l'app où un chiffre exact s'affiche comme une
    /// estimation.
    func testDesKcalManuellesNOntPasDeTilde() {
        let fil = DuoFeedBuilder.build(
            meals: [.init(publicID: "M1", date: midi, slot: .dinner,
                          title: "Poisson et purée", kcal: 510, isManual: true)],
            activities: [])
        XCTAssertEqual(fil[0].subtitle, "dîner, 510 kcal")
    }

    /// Le remplissage des identifiants vides (spec §3.4). La fonction rend AUSSI la
    /// liste des attributions à persister : le constructeur est pur, c'est l'appelant
    /// qui écrit dans le magasin.
    func testLesIdentifiantsVidesSontAttribuesEtRemontes() {
        let resultat = DuoFeedBuilder.assignMissingIDs(
            meals: [.init(publicID: "", date: midi, slot: .lunch,
                          title: "Pâtes", kcal: 600, isManual: false)],
            activities: [.init(publicID: "A1", date: apresMidi, title: "Marche",
                               durationMinutes: 30, xp: 30)],
            newID: { "NEUF" })
        XCTAssertEqual(resultat.mealIDs, ["NEUF"])
        XCTAssertEqual(resultat.activityIDs, ["A1"])
    }

    /// Deux entrées vides ne doivent PAS recevoir le même identifiant : c'est
    /// précisément l'accident que la chaîne vide en défaut de déclaration évite,
    /// et il serait absurde de le réintroduire ici.
    func testDeuxEntreesVidesRecoiventDesIdentifiantsDistincts() {
        var compteur = 0
        let resultat = DuoFeedBuilder.assignMissingIDs(
            meals: [.init(publicID: "", date: midi, slot: .lunch,
                          title: "Pâtes", kcal: 600, isManual: false),
                    .init(publicID: "", date: apresMidi, slot: .snack,
                          title: "Fruit", kcal: 80, isManual: false)],
            activities: [],
            newID: { compteur += 1; return "ID\(compteur)" })
        XCTAssertEqual(Set(resultat.mealIDs).count, 2)
    }

    func testUnFilVideResteVide() {
        XCTAssertTrue(DuoFeedBuilder.build(meals: [], activities: []).isEmpty)
    }
}
